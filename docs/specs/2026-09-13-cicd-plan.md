# GitHub Actions CI/CD 实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 让 push 到 main 自动跑测试并产出不可变镜像（tag = git sha），部署时手动触发一次 SSH 拉取重建，保证线上跑的必然是新代码且不丢数据。

**Architecture:** CI 在 GitHub runner 上跑（含 PostgreSQL service container，顺带让 Flyway 从零验一遍迁移脚本），构建两个镜像推 GHCR；CD 通过 SSH 到服务器执行一个幂等的 `deploy.sh`，用 sha tag 保证重建、按 OCI label 清理旧镜像（不伤同机其他项目）、绝不动数据卷。

**Tech Stack:** GitHub Actions（actions/checkout@v4、setup-java@v4、setup-node@v4、docker/build-push-action@v6）、GHCR、Docker Compose v5.5.0、Cloudflare Origin Certificate。

**Spec:** [docs/specs/2026-09-13-cicd-design.md](2026-09-13-cicd-design.md)

## Global Constraints

以下约束适用于**每一个**任务，不再逐条重复：

- ⚠️ **绝不执行 `docker compose down -v`**。`doc-qa-pg-data`（对话记录/用户）与 `doc-qa-app-data`（已上传的知识库文件）必须保留。任何清理动作前先想清楚它会不会碰到卷。
- ⚠️ **不碰同机其他项目**。服务器上还有 `orientation` 项目（占 3001 端口）。清理镜像必须按 OCI label 过滤，不用 `docker image prune -a`、不按名字 grep。
- ⚠️ **服务器地址、密码、任何密钥都不得进入版本库**。文档与代码里一律用 `<SERVER_HOST>` 指代；真实值只存在于 GitHub Secrets 与服务器上的 `.env`（`chmod 600`）。
- **镜像 tag 用 git sha，`latest` 只作标记不作部署依据。**
- **生产 profile 的 `spring.flyway.locations` 只含 `classpath:db/migration`**，绝不含 `db/dev-migration`（那里是密码为 `demo123` 的演示账号）。
- 本地 `mvn` 前必须 `JAVA_HOME="D:/IDEAjava/JDK/jdk17"`（默认 JDK 23 与 Lombok 1.18.30 不兼容）。
- git 提交信息格式 `type(scope): subject`，中文描述，**不包含任何 Claude 相关元信息**。
- 提交前确认 `git status` 里没有 `.env` / `certs/` / 私钥。

- [ ] **Step 2: 改 `doc-qa-web/nginx.conf`，把 server 块改成 80 跳转 + 443 承载**

在现有 `server { listen 80; ... }` 块**之前**插入跳转块，并把原块的 `listen 80;` 改为 `listen 443 ssl;` 且补上证书与协议配置：

```nginx
# 80 端口只做跳转。Cloudflare 配的是 Full (strict)，回源走 443；
# 保留这个块是为了「万一 CF 模式被改回 Flexible 时不会出现明文入口」
server {
    listen 80;
    server_name _;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    server_name _;

    # Cloudflare Origin Certificate。由 CF 签发（免费、15 年），CF 回源时校验它，
    # 所以不需要浏览器信任 —— 浏览器那一侧的证书由 CF 边缘提供
    ssl_certificate     /etc/nginx/certs/origin.crt;
    ssl_certificate_key /etc/nginx/certs/origin.key;

    ssl_protocols       TLSv1.2 TLSv1.3;
    ssl_ciphers         HIGH:!aNULL:!MD5;
    ssl_session_cache   shared:SSL:10m;
    ssl_session_timeout 10m;

    # ↓↓↓ 以下到文件末尾与改动前完全一致，只字未改 ↓↓↓
    root /usr/share/nginx/html;
    index index.html;

    client_max_body_size 5m;

    location / {
        try_files $uri $uri/ /index.html;
    }

    location /assets/ {
        expires 1y;
        add_header Cache-Control "public, immutable";
    }

    location /api/ {
        proxy_pass http://app:8080/;

        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        proxy_buffering off;
        proxy_cache off;
        proxy_set_header Connection "";
        proxy_read_timeout 3600s;
        proxy_send_timeout 3600s;

        chunked_transfer_encoding on;
    }
}
```

⚠️ **不要把原有的中文注释删掉**——那些注释（client_max_body_size 为什么是 5m、SSE 为什么要关 proxy_buffering）记录了只有真跑起来才会暴露的坑，是这个项目最有价值的文档。

### Task 4: CI 流水线

**Files:**
- Create: `.github/workflows/ci.yml`

**Interfaces:**
- Produces: GHCR 上的两个镜像 `ghcr.io/renhao-wan/doc-qa-service-api` 与 `-web`，tag 为对应 commit 的 git sha。Task 5 的部署依赖这两个 tag 存在。

- [ ] **Step 1: 创建 `.github/workflows/ci.yml`**

```yaml
name: CI

on:
  push:
    branches: [main]
  pull_request:
  workflow_dispatch:

jobs:
  backend:
    name: 后端测试
    runs-on: ubuntu-latest
    services:
      # ⚠️ 必须起：项目里 11 个测试类是 @SpringBootTest，会连 localhost:5432。
      #    runner 上没有数据库的话 CI 会一片红。
      #    顺带的好处：库是空的，Flyway 会在测试启动时从零建表，
      #    等于每次 push 都把三份迁移脚本在干净环境里验一遍。
      postgres:
        image: pgvector/pgvector:pg16   # 官方 postgres 镜像不含 pgvector
        env:
          POSTGRES_DB: robot
          POSTGRES_USER: postgres
```

- [ ] **Step 1: 创建 `scripts/deploy.sh`**

```bash
#!/usr/bin/env bash
#
# 服务器侧的部署脚本。由 GitHub Actions 通过 SSH 调用，也可以人工执行。
#
# 幂等：重复执行同一 IMAGE_TAG 不会产生副作用。
#
# ⚠️ 本脚本绝不删除数据卷。doc-qa-pg-data（对话记录）与 doc-qa-app-data（知识库文件）
#    在容器重建后必须原样保留 —— 这就是全程只用 `up -d` 而不用 `down -v` 的原因。
set -euo pipefail
cd "$(dirname "$0")"

echo "==> 部署开始：$(date '+%F %T')"

# ── 前置校验：缺什么就明确报错，不要带着半截配置往下跑 ──
[[ -f .env ]]             || { echo "❌ 缺 .env"; exit 1; }
[[ -f certs/origin.crt ]] || { echo "❌ 缺 certs/origin.crt（Cloudflare Origin Certificate）"; exit 1; }
[[ -f certs/origin.key ]] || { echo "❌ 缺 certs/origin.key"; exit 1; }
grep -q '^IMAGE_TAG=..*'  .env || { echo "❌ .env 里没有 IMAGE_TAG"; exit 1; }

# ⚠️ 不要写 source .env：那会把 .env 当脚本执行，密钥里若含 $ 或空格会被
#    二次展开、可能静默改值。compose 自己会读 .env 做变量替换，
#    这里只取出 IMAGE_TAG 用于日志和后面的清理过滤
IMAGE_TAG=$(grep '^IMAGE_TAG=' .env | cut -d= -f2-)
export IMAGE_TAG
echo "==> 目标镜像 tag：${IMAGE_TAG}"

# ── 拉取镜像 ──
docker compose pull

# ── 重建变化的容器 ──
# ⚠️ 绝不加 -v：会连数据卷一起删
# --remove-orphans：compose 文件里删掉的服务，其容器一并回收，不留僵尸
docker compose up -d --remove-orphans

# ── 清理本项目旧镜像 ──
# ⚠️ 不能直接 `docker image prune -a`：这台机器上还有 orientation 项目，
#    那样会把它的镜像一起删掉。按构建时打的 OCI label 精确过滤，
#    且只清 72 小时内没被用过的 —— 留出「想回滚到上上个版本」的窗口
echo "==> 清理 72 小时前的旧镜像（按 label 过滤，不影响同机其他项目）"
docker image prune -af \
  --filter "label=org.opencontainers.image.source=https://github.com/renhao-wan/doc-qa-service" \
  --filter "until=72h"

# ── 健康检查 ──
# ⚠️ 不做这一步的话，「容器起来了但其实是坏的」会显示成部署成功
echo "==> 等待 web 就绪"
for i in $(seq 1 30); do
  if curl -fsS -k https://localhost/ -o /dev/null 2>/dev/null; then
    echo "==> ✅ web 健康检查通过"
    break
  fi
  if [[ $i == 30 ]]; then
    echo "❌ web 在 150 秒内未就绪，部署失败"
    docker compose ps
    docker compose logs --tail=50 web app
    exit 1
  fi
  sleep 5
done

echo "==> 当前容器状态："
docker compose ps
echo "==> ✅ 部署完成：${IMAGE_TAG}（$(date '+%F %T')）"
```

- [ ] **Step 2: 创建 `.github/workflows/deploy.yml`**

```yaml
name: Deploy

# 仅手动触发。刻意不挂 push —— 避免半成品提交直接上生产
on:
  workflow_dispatch:
    inputs:
      image_tag:
        description: '要部署的镜像 tag（git sha）。留空则部署当前 ref 的 HEAD'
        required: false
        default: ''
        type: string

jobs:
  deploy:
    name: 部署到生产服务器
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: 解析目标镜像 tag
        id: tag
        run: |
          if [[ -n "${{ inputs.image_tag }}" ]]; then
            echo "value=${{ inputs.image_tag }}" >> "$GITHUB_OUTPUT"
          else
            echo "value=${{ github.sha }}" >> "$GITHUB_OUTPUT"
          fi

      - name: 准备 SSH
        run: |
          mkdir -p ~/.ssh
          echo "${{ secrets.SSH_PRIVATE_KEY }}" > ~/.ssh/deploy_key
          chmod 600 ~/.ssh/deploy_key
          ssh-keyscan -H "${{ secrets.SERVER_HOST }}" >> ~/.ssh/known_hosts 2>/dev/null

      - name: 同步编排文件与部署脚本
        run: |
          scp -i ~/.ssh/deploy_key \
            docker-compose.yml scripts/deploy.sh \
            "${{ secrets.SERVER_USER }}@${{ secrets.SERVER_HOST }}:/opt/doc-qa-service/"

      - name: 写入 .env
        # ⚠️ 走 stdin 而不是 ssh 命令行参数：命令行参数会出现在服务器的进程列表里
        #    （ps 可见）。GitHub Actions 会自动对 secrets 打码，日志侧是安全的
        run: |
          ssh -i ~/.ssh/deploy_key \
            "${{ secrets.SERVER_USER }}@${{ secrets.SERVER_HOST }}" \
            "cat > /opt/doc-qa-service/.env && chmod 600 /opt/doc-qa-service/.env" <<EOF
          IMAGE_TAG=${{ steps.tag.outputs.value }}
          SPRING_PROFILES_ACTIVE=prod
          WEB_HTTP_PORT=80
          WEB_HTTPS_PORT=443
          DASHSCOPE_API_KEY=${{ secrets.DASHSCOPE_API_KEY }}
          JWT_SECRET=${{ secrets.JWT_SECRET }}
          SEARXNG_SECRET=${{ secrets.SEARXNG_SECRET }}
          EOF

      - name: 执行部署
        run: |
          ssh -i ~/.ssh/deploy_key \
            "${{ secrets.SERVER_USER }}@${{ secrets.SERVER_HOST }}" \
            "cd /opt/doc-qa-service && bash deploy.sh"

      - name: 部署结果摘要
        if: always()
        run: |
          echo "### 部署 ${{ job.status }}：\`${{ steps.tag.outputs.value }}\`" >> "$GITHUB_STEP_SUMMARY"
```
