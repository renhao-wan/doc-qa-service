# 选型与取舍

本文记录两类决策：

- **第一块｜为什么这么做**——当前实现背后的理由
- **第二块｜为什么不那么做**——被否决的方案，以及否决它们留下的代价

第二块通常更有价值。项目的长期维护者最容易问的是「当初怎么不考虑 XX」，而这类答案往往只存在于当时的讨论里，代码和提交信息都留不下痕迹。**被否决不等于被否定**——每一条都附了它留下的代价，将来条件变了可以重新评估。

> 素材来自各设计文档与执行期的决策台账。凡无法从当前代码直接验证的「当时的判断」，均按当时结论如实记录，不冒充客观事实。

# 第一块 · 为什么这么做

## 1. 为什么手写 `CustomChatMemoryAdvisor`，而不用 Spring AI 内置的 ChatMemory

Spring AI 提供了 `ChatMemory` / `MessageChatMemoryAdvisor`，直接用能省掉一个类。

**理由**：对话历史在本项目里**本来就是业务数据**——它落在 `t_chat_message`，要支持分页查询、重命名、级联删除。用内置 ChatMemory 等于维护两份存储，还得处理双写一致性。

**代价**：多写一个 Advisor，并且要自己处理 token 预算（见下一条）。

## 2. 为什么对话记忆要同时有「条数上限」和「token 预算」

`LIMIT 50` 只约束**条数**，不约束长度。50 条消息如果每条都很长（用户贴了一整篇文档、模型回了一大段），拼出来的 prompt 可以远超模型上下文窗口，表现为模型 API 返回 400、SSE 流转 error。

**理由**：条数上限是**查库边界**，token 预算才是**上下文边界**，两者管的是不同的事，不能互相替代。

裁剪策略有三处非平凡的选择：从最新往旧累加（越近越重要）、单条超预算时至少留一条（否则用户贴长文时这轮退化成无记忆）、丢掉开头不完整的轮次（避免「有答无问」的历史让模型把半截内容当成凭空出现的陈述）。

**代价**：用 JTokkit 估算 token 对中文只是**近似**（OpenAI 的 BPE 词表）。接受的原因是这里不需要精确记账，只需要「足够接近以便在撑爆之前触发截断」；精确方案要么依赖模型自己的 tokenizer（本项目按请求动态指定模型名，拿不到对应词表），要么自建词表，维护成本远高于收益。

## 3. 为什么 `ChatClient` 是每个请求现场构造的

`ChatClientConfig` 注册了一个 `chatClient` Bean，但两个 Controller **都不用它**。

**理由**：模型名与 temperature 需要**按请求动态指定**（对话页由前端传参，知识库页取配置）。共享单例就得在其中维护可变状态，反而更糟。

**代价**：每个请求新建一次 `OpenAiChatModel`，牺牲了一点对象复用。相对它换来的灵活性可以接受——真正的开销在网络调用上。

## 4. 为什么两个线程池的拒绝策略不同

联网抓取天然是 IO 密集与 CPU 密集混合的，项目把它拆成两段：

| 线程池 | 类型 | 拒绝策略 |
|---|---|---|
| `httpRequestExecutor` | IO 密集 | `CallerRunsPolicy` |
| `resultProcessingExecutor` | CPU 密集 | `AbortPolicy` |

**理由**：

- **IO 密集用 `CallerRunsPolicy`**：任务是网络等待，压垮线程池也不会压垮 CPU；队列满了让调用线程自己跑，相当于**给上游一个自然的减速带**，任务不会丢。若用 `AbortPolicy`，搜索高峰会直接抛异常，用户看到问答失败。
- **CPU 密集用 `AbortPolicy`**：解析任务实打实吃 CPU，队列堆积意味着响应时间雪崩。此时**快速失败比慢慢排队更有价值**——排队的任务即使最终执行完，用户也早就不等了。

参数方向也相反：IO 池给大核心数与大队列（50 / 1000）容忍等待，CPU 池核心数贴着核数、队列只给 200 避免堆积。

## 5. 为什么 RAG 的 `topK` 固定为 3

**理由**：不是拍的，是实测出来的——见 `rag-evaluation/report.md` 的对照数据。`topK` 做成配置项而非写死，正是为了让「取多少合适」能被实测决定。

**代价**：这个值是基于**三份中文公文、25 道题**的语料得出的。换成表格密集或结构扁平的文档，最优值可能不同。

## 6. 为什么用 `RequestAttributeSecurityContextRepository`

两个 SSE 接口返回 `Flux`，流跑完后 Tomcat 会做一次 ASYNC dispatch，把整条 Spring Security 过滤链重跑一遍。而 Spring Security 6 的 `SecurityContextHolderFilter` 只从仓库读、**不往回写**，`JwtAuthenticationFilter` 在 ASYNC 时又被 `OncePerRequestFilter` 默认跳过——叠加起来，那一遍读不到身份，会退化成匿名并被拒，每个 SSE 请求稳定产生 3 条 ERROR 堆栈。

**理由**：请求属性作用域天然随请求结束而消失，**不跨请求、不建会话**，但仍能在同一次请求的 ASYNC dispatch 中被读到。

**为什么不选另一个显而易见的方案**：默认的 `DelegatingSecurityContextRepository` 内含 `HttpSessionSecurityContextRepository`，会在保存时建出 `HttpSession`，与 `SessionCreationPolicy.STATELESS` 的意图直接冲突。

**代价**：`securityContextRepository()` 这个 `@Bean` 方法**必须保持 `static`**——`SecurityConfig` 构造器依赖 `JwtAuthenticationFilter`，过滤器又依赖这个 Bean，写成实例方法即循环依赖、启动失败。这是一处容易被「顺手重构」掉的脆弱点，代码里已写明。

## 7. 为什么索引排序键用 `id` 而不是 `create_time`

**理由**：`id` 是 `BIGSERIAL`，单调递增且唯一。`create_time` 可能重复（同一毫秒落两条），**排序值相等时 `LIMIT` 取哪几条是不确定的**，分页时会因此出现重复或遗漏。

**代价**：`id` 是物理顺序，语义上不表达"时间"。对外展示仍用 `create_time`。

## 8. 为什么消息落库用 `doFinally` 而不是 `doOnComplete`

Reactor 流有三种终止信号，用户点「停止生成」触发的是 `ON_CANCEL` 而非 `ON_COMPLETE`。

**理由**：`doFinally` 是唯一能同时覆盖三种信号的回调。原实现只在 `doOnComplete` 里落库，导致用户中止时**整轮对话丢失**（问一句、答一半、点停止、刷新页面，什么都没了）。

**代价**：需要在回调里自己判断信号类型——`ON_ERROR` 时不落库（半截回答写进去意义不大，且用户没看到）。

## 9. 为什么要做「覆盖式重建」而不是「跨文件去重」

这里曾经用「逐条 `topK=1` 相似检索、得分 > 0.99 视为重复并跳过」做去重。

**为什么废弃它**：那是**跨文件**去重——同一段文本只归属于第一个上传它的文件。而删除走 `mdStorageId == id`，于是删掉 A 文件会连带删掉 B 文件里那段「被判定为重复」的内容，**B 从此检索不到自己的段落**。这是归属错乱，是正确性问题，不只是性能问题。

**现在的做法**：写入前先按 `mdStorageId` 删掉该文件的旧向量，再整体批量写入。一个文件的向量就是它当前内容的向量，与别的文件无关。

**代价**：重复内容在多份文件里会各存一份向量，牺牲少量存储换取归属正确。

## 10. 为什么归属条件要「融进查询」而不是「查完再比对」

对话侧的越权防护写成 `WHERE user_id = ?` 直接进查询条件，越权自然退化成「查不到」。

**理由**：一个手法买到三件事——代码最少、天然防越权、**不泄露资源是否存在**（A 删 B 的对话得到「此对话不存在」，而不是「无权操作」）。

**但它不适用于知识库文件**：文件是共享可见的，加 `WHERE uploader_id = ?` 会让列表只剩自己的。所以那两处**必须显式比对**并返回「无权操作」。**越权该不该泄露资源存在性，取决于该资源本来就对操作者可见与否**——这两条路径的差异是刻意的。

## 11. 为什么用「改签名」而不是「加重载」

加用户维度时，`ChatMapper.selectPageList` / `touchUpdateTime` 都是**改签名**，不是新增一个带 `userId` 的重载。

**理由**：如果保留旧方法再加新方法，旧方法 `selectPageList(current, size)` 就是一条**现成的越权入口**——只要有一处调用点漏改，漏洞就成立。改签名让编译器强制所有调用点更新，从根上消灭这类遗漏。

**代价**：调用点必须一次性全部改完（本项目各只有一个调用点，成本很低）。**这条做法值得在类似场景里沿用。**

## 12. 为什么幂等写入用 `ON CONFLICT DO NOTHING` 而不是捕获异常

前端是 3 路并发上传分片，「先查再插」存在竞态窗口。

**理由**：以**影响行数**判断是否首次写入，由唯一索引做最终裁决。

**为什么不能改成捕获 `DuplicateKeyException`**：PostgreSQL 中约束冲突会让整个事务进入 **aborted 状态**，后续语句全部失败；而该方法是 `@Transactional` 的，方法内 catch 也救不回来。

## 13. 为什么演示账号必须放在单独的迁移目录

**理由**：Flyway 的迁移脚本是**跨环境同一份**的。把演示账号的 `INSERT` 放进 `db/migration/`，就等于给生产库插两个密码可公开推知的登录凭证。所以它必须待在只有开发环境会扫到的 `db/dev-migration/`。

**代价**：

- 这个目录带来两条隐蔽的版本号约束（新增生产迁移必须从 V4 开始；生产库绝不能被 dev profile 碰过），见 `modules/data.md` §5.3。
- **生产库第一次部署完是空的**：`t_user` 里没有任何账号，站点能打开、登录页能渲染，但**谁也登不进去**。账号必须由管理员手工创建一次（步骤见 `deployment.md` §8.2），换服务器时还要重做。

第二条看着像麻烦，其实是第二块 §10「账号由管理员分配」的另一面——演示账号能**自动**进生产库，那才是真的出问题。

## 14. 为什么错误码要先分段

`1xxxx` 通用 / `2xxxx` 业务 / `3xxxx` 鉴权。

**理由**：错误码是**对外契约**的一部分（前端拦截器按 `errorCode` 判断行为），分段让新增错误码时有明确的归属位置，不至于随手插在末尾。前端 `AUTH_ERROR_CODES = ['30001']` 能写成一个短列表，正是因为鉴权类错误集中在 `3xxxx` 段。

# 第二块 · 为什么不那么做

## 1. 不新增 `AUTH_ACCESS_DENIED("30002")`

`AccessDeniedHandler` 返回的是 `SYSTEM_ERROR`（10000）而非鉴权类错误码，语义上错位。评审建议加一个 `30002`。

**否决理由**：设计文档里的错误码表是**权威清单**，擅自扩充会让文档与实际不符；且当前没有用 `@PreAuthorize`，该处理器**不可达**。

**代价**：将来启用方法级权限时，需要回头把它改对。

## 2. 不排除 `UserDetailsServiceAutoConfiguration`

Spring Boot 检测到 security starter 且没有自定义用户时会生成一个随机密码，启动日志里有一条 `Using generated security password` 的 WARN。消除它需要在配置里排除该自动配置。

**否决理由**：该默认用户**不可利用**（`httpBasic` 与 `formLogin` 已 disable，唯一 `permitAll` 端点走本项目自己的 `AuthService`）；属 YAGNI。

**代价**：这条 WARN 会一直存在。**它不是「过几轮就会消失的临时噪音」**——曾经有人这样判断过，是错的。

## 3. 不给 `mergeChunk` 加状态门控

`mergeChunk` 不校验 `uploader_id`，是知识库侧唯一能改写他人既有记录的路径。一个自然的修法是「主记录状态不是 `UPLOADING` 时拒绝合并」。

**否决理由**：**行为变更、无测试覆盖、可能破坏合法的重传场景**。合法续传正是发生在 `UPLOADING` 状态（此时 `stored_file_name` 还是空串，覆盖它没有副作用），而门控会把某些边界情况一并拒掉。

**代价**：该缺口仍可利用——对已 `COMPLETED` 文件的覆盖会把别人已被全体用户检索到的正文整体替换。**缓解措施只是把缺口写进方法 Javadoc**，让改动这个方法的人先看到它。

**这条值得记住的是判断方式**：当一个修法会改变行为、又没有测试能证明它没改坏别的场景时，**记录缺口比匆忙修复更负责**。

## 4. 不给 `t_chat_message` 加 `user_id`

**否决理由**：冗余——归属已在所有入口把关；加列会让「按 `chat_uuid` 取最近 N 条」这个**热路径**多一层无意义的过滤条件。

**代价**：无。

⚠️ 记录这条的真正目的是留下一个判断：**不建议后续为「看起来更安全」而随手加列**。安全边界应该在入口处收口，而不是在每个表上都撒一层冗余字段。

## 5. 迁移脚本不包 `BEGIN` / `COMMIT`

**否决理由**：全部语句幂等可重跑，`psql -v ON_ERROR_STOP=1` 已保证不出现残缺态；将来 Flyway 接管时会自带事务语义，此时叠加属重复。

**代价**：无。

## 6. 登录成功后不回跳被拦截前的目标页

未登录访问知识库页 → 登录后落到首页，需要再点一次。

**否决理由**：属功能增强而非缺陷；当时处在多任务改造中，不宜扩大变动面。

**代价**：一次多余的点击。

## 7. 不加 `await` 或空 `catch` 去消除 unhandled rejection

`onopen` 里 `throw` 出的错误会让 `fetchEventSource` 返回的 Promise reject，而两处调用点都没有 `await`，于是控制台有一条 unhandled promise rejection。

**否决理由**：**这是预期内、无害的**——`router.push('/login')` 在 throw 之前已执行，跳转正常。

⚠️ **明确禁止这样"修"**：加了 `await` 会让异常落进 `catch` 块，把用户消息改写成「抱歉，请求出错了」——那会**掩盖「已跳转登录页」的事实并给出不准确的文案**。一个"消除控制台报错"的动作，代价是让用户看到错误的原因。

**代价**：控制台留一条 unhandled rejection。**这是刻意保留的。**

## 8. 不修 `onopen` 非 30001 分支的加载态卡死

当响应不是事件流、且错误码不是 30001 时，助手气泡会永久转圈、无用户可见提示。

**否决理由**：① 触发条件最现实的来源是归属校验失败，而**改动前症状完全相同**（非回归）；② 最直觉的修法（加 `await` / 空 `catch`）正是上一条禁止的；③ 与当时的任务目标正交。

**代价**：非法 `chatId` 等场景下用户看到永久转圈。

## 9. 不做自动回滚

**否决理由**：「回滚 = 重跑部署流程并填上一个成功的 sha」，一次点击的成本已经够用。自动回滚需要在服务器上维护「上一个健康版本」的状态与判定逻辑，**复杂度不匹配当前阶段**。

**代价**：回滚依赖人工判断"该退到哪个版本"。

## 10. 不做注册、refresh token、登出黑名单、RBAC、限流

| 不做 | 理由 |
|---|---|
| 注册接口 | 定位是企业内部系统，账号由管理员分配更贴合真实场景；演示用预置账号已够 |
| refresh token | 超出预估工时，且对项目的边际收益低于把主线链路做扎实 |
| 登出黑名单 | 需要额外存储与清理策略；前端清 token 已满足当前需求 |
| 角色 / 细粒度权限 | 当前只有「文件删改限上传者」一处需要权限判断，引入 RBAC 是过度设计 |
| 登录限流与防爆破 | 真实生产必需，但与「会话隔离」这个目标正交，强行塞入会让改动面失控 |

**整体代价**：JWT 无法主动失效——签发后在有效期内始终有效，改密码或强制下线都做不到。这是选择无状态 JWT 的固有代价，也是「为什么需要 refresh token / 黑名单」的切入点。

## 11. 不给 `uploader_id` 建索引

**否决理由**：文件列表是全局共享的（无用户过滤），删改校验走主键查询后在内存比对，都用不上。

**代价**：无。

## 12. 不改 SSE 接口的 `produces`

如果测试里出现 406，最直接的反应是放宽 `produces` 或加 `.accept(MediaType.ALL)`。

**否决理由**：`produces` 是对外契约，为了测试方便而放宽它是本末倒置。

**代价**：无。RED 阶段实际**没有出现 406**，预备方案未启用。

## 13. 不用 `git add -f` 强推被排除的文档

`CLAUDE.md` / `TODO.md` 被 `.gitignore` 明确排除（注释写明"仅本地使用"）。

**否决理由**：这是项目所有者**在计划开始前的明确决定**，强推会把内部内容推上公开仓库，且**不可逆**。

**代价**：这两份文档的更新只存在于本机，换机器 clone 不会跟着走。

## 14. 不把未验证的东西写成"已通过"

验收记录里曾出现「分片上传回归通过」，而实际覆盖的是**人工构造的分片**（验的是合并逻辑），不是前端真实路径——真实 `CHUNK_SIZE = 2MB` 的分片会撞上 multipart 上限。

**否决理由**：验收记录是要被拿去讲的内容。写"通过"而实际传不上去，会被问穿；**如实记录比好看更重要**。

**代价**：记录看起来"不完美"。这是它应有的样子。

## 15. 不继续在 `.me` 域名上排查

站点访问失败（CF 报 525 / 403）时，最初的判断是「Cloudflare 配错了」，把它当成配置问题来解——`Flexible`、`Full (strict)` 挨个试过一遍。

**否决理由**：`.me` 后缀**不在工信部批复的顶级域名列表里**，在大陆**根本无法备案**。未备案的域名一旦回源到大陆服务器就会命中 ICP 拦截，这是**链路上的事，不是配置的事**——把 CF 的 SSL 模式试遍也不会有解。继续在配置层面排查，等于在一个不可能有解的方向上消耗时间。

**代价**：要改 NS、按新域名重签源站证书（想用 `Full (strict)` 的话）、在 CF 重建 DNS 记录，且 NS 切换有一段等待期。但这是一次性的，而「域名随时可能被拦」是持续的。

## 附：一条跨领域的判断

上面多条决策共享同一个思路，值得单独指出：

> **把安全约束做成编译器强制的，而不是靠约定。**
> （见第一块 §11、第二块 §4）

改签名而不是加重载、把归属融进查询而不是事后比对、不在每张表上撒冗余字段——它们指向同一件事：**让"漏做"在编译期或查询层就不可能发生，而不是指望每个未来的改动者都记得住**。

与之互补的另一条：**当"修复"会改变行为且没有测试能证明它没改坏别的场景时，记录缺口比匆忙修复更负责**（第二块 §3）。
