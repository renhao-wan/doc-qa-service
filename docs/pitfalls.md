# 坑点合集

这里收的是**跨模块与环境级**的问题——复现它们需要理解多个模块，或者根本不涉及业务代码。

**模块内的坑不在这里**，就近写在各模块文档里：

- 对话链路的坑 → `modules/chat.md` §7
- 知识库链路的坑 → `modules/knowledge-base.md` §8
- 鉴权与隔离的坑 → `modules/auth.md` §8
- 数据层与迁移的坑 → `modules/data.md` §8

这些坑有一个共同特征：**现象指向的方向，往往与真实原因相反**。所以每条都写得比较具体——包含可识别的报错文本或表现，你才能在遇到时认出它。

---

## 1. 构建：`JAVA_HOME` 必须指向 JDK 17

**现象**：`mvn` 报几十个编译错误，全是 Lombok 生成的方法「找不到符号」—— `log` 变量、`builder()`、`setXxx()` 等等。**看起来像包名或依赖问题，但不是。**

**原因**：Lombok 1.18.30 最高只支持 JDK 21，而本机默认的 `JAVA_HOME` 指向更高版本时，注解处理器无法工作，Lombok 生成的一切都不存在。

**怎么避免**：构建前显式指定。

```bash
JAVA_HOME="<你的JDK17路径>" mvn clean package -DskipTests
```

**注意**：Docker 镜像构建**不受此影响**——`Dockerfile` 内部用的是 `maven:3.9-eclipse-temurin-17`，与宿主机 `JAVA_HOME` 无关。这条约束只适用于在宿主机直接跑 `mvn`。

**将来的升级路径**：若要用 JDK 21+，需**同时**把 Lombok 升到 1.18.34+ 并给 `maven-compiler-plugin` 配置 `annotationProcessorPaths`——JDK 21 起 javac 不再从 classpath 自动发现注解处理器，只升 Lombok 版本不够。

---

## 2. 构建：两类「找不到符号」，表象相似、成因完全不同

IDE 里报大量「找不到符号」，有两种成因，**排查方向完全相反**：

| | 假诊断 | 真错误 |
|---|---|---|
| 成因 | IDEA 未正确处理 Lombok 注解处理器（常与 JDK 版本混用有关） | **公共类/接口名与文件名不匹配** 等编译错误，连带 Lombok 注解处理**整体中断** |
| 表现 | IDE 标红一片 | 报出**几十行级联**「找不到符号」 |
| 验证 | 命令行 `mvn` **全程 BUILD SUCCESS** | `mvn` 同样失败，但**第一行**才是真错误 |

**为什么危险**：后者的级联错误与前者（乃至与上面那条 JDK 版本问题）**高度相似**。真实的失败案例是：一次批量重命名中，重命名表与标识符替换表的要求相互冲突，导致 `KnowledgeBaseService.java` 里声明的却是一个名为 `KnowledgeBase` 的公共接口——文件名对不上，javac 报错，随后 Lombok 注解处理整体中断，刷出 80 行「找不到符号 `log` / `getXxx()`」。

**怎么避免**：**永远往下翻到第一条错误**。级联错误的根因永远在最前面，Lombok 相关的报错几乎总是**第二层**症状。

## 3. 构建：Maven 本地仓库可能不在默认位置

**现象**：明明依赖已经下载过，`mvn` 仍报找不到某个库（或找到的是很旧的版本）。

**原因**：本机的 `settings.xml` 把本地仓库指向了**非默认目录**，而不是 `~/.m2/repository`。后者里可能只有历史残留的旧版本 jar，于是「看起来没有解析依赖」。

**怎么避免**：核对 `settings.xml` 的 `<localRepository>`，并在排查依赖问题时以它为准。找不到依赖时先确认自己看的是哪个目录。

---

## 4. 排查：端口上跑的可能不是你以为的那个进程

**现象**：带了正确 token 调接口，仍返回「登录状态已失效」；或者登录接口返回一个通用错误。

**原因**：**那个端口上跑的是一个更早启动、代码更旧的实例**。真实发生过：旧实例（早于鉴权改造）一直占着应用端口，任何手工联调都表现为「改造没生效」，而代码本身完全正确。

**怎么避免**：改代码后手工验证前，先确认**端口上跑的是当前构建**。判断方法：看启动日志里有没有你刚改的东西；或者调一个只有新代码才有的接口。**不要默认端口上就是自己刚起的那个。**

## 5. 鉴权：放行清单不含 `/error`，过滤器必须自己吞掉解析异常

**现象**：一个本该是「token 无效」的请求，返回了某个**不相关的**错误；或者原始错误被掩盖。

**原因**：Security 过滤器链内部抛出的**非安全类**异常会触发 ERROR dispatch 到 `/error`，而该路径**同样要求认证**（放行清单里只有 `/auth/login`）。于是原始错误被替换成了鉴权错误。

**怎么避免**：`JwtAuthenticationFilter` 必须**自己 catch** 解析异常，而不是让它冒泡：

```java
} catch (ExpiredJwtException e) {          // 过期：单独 catch，日志里可区分
    log.info("## token 已过期: {}", e.getMessage());
    SecurityContextHolder.clearContext();
} catch (JwtException | IllegalArgumentException e) {   // 签名无效 / 格式错误 / null / 空串
    log.warn("## token 无效: {}", e.getMessage());
    SecurityContextHolder.clearContext();
}
```

`IllegalArgumentException` 这一支不能省：它覆盖 `token` 为 null/空串，以及 `sub` 非数字时 `Long.valueOf` 抛出的 `NumberFormatException`。

## 6. 前后端契约：`PageResponse` 没有 `records` 层

**现象**：前端拿不到分页数据，或者取到 `undefined`。

**原因**：`PageResponse<T> extends Response<List<T>>`——**记录数组直接挂在 `data` 上**，与 `total` / `size` / `current` / `pages` **平级**。它**没有** `records` 这一层（那是 MyBatis-Plus `Page` 对象的结构）。

```json
{ "success": true, "data": [ ... ], "total": 42, "size": 10, "current": 1, "pages": 5 }
```

**怎么避免**：写前端取数逻辑时注意这个差异。这是本项目被反复点名的**最常见踩坑点**。

## 7. 测量：hash 路由下的同文档导航不触发 reload

**现象**：验证「token 失效会自动跳登录页」时，行为看起来**没有发生**。

**原因**：路由是 hash 模式。从 `#/` 导航到 `#/` 属于**同文档导航，不触发页面 reload**。如果测试依赖「刷新页面」来观察拦截器行为，会得到**假阴性**。

**怎么避免**：需要触发真实重新加载时，用 `location.reload()` 而不是再 `goto` 一次相同的 hash 地址。

**这是本项目手工验证里出现过的唯一一个测量陷阱**，验证同类行为时要注意。

## 8. 方法论：对框架默认行为的预测，都是估计值

**现象**：按文档写好的「预期结果」与实际跑出来的不一样。

**实例**（都真实发生过）：

- 预期未认证返回 401，**实际是 403**
- 预期某个测试拿到 2 条数据，**实际是 6 条**（漏算了迁移回填的存量）
- 预期某一步会编译失败，**实际不会**（前一步已经加好了字段）

**怎么避免**：把「预期」当作**待验证的假设**，而不是事实。当实测与预期不符时，**先查清是哪一边错了**——是代码有问题，还是预期本身就拍错了。上面几例最后都被判定为「预期错、实现对」。

---

## 9. 前端：`@press-enter` 会绕过表单校验

**现象**：用户名留空、焦点在密码框时按回车，请求**直接发出**，后端返回参数校验错误，原始文案糊在界面上。

**原因**：`@press-enter` 直接绑了提交处理函数，**绕过了 `a-form` 的 `rules`** 校验。

**怎么避免**：删掉 `@press-enter`。`a-form` 渲染的是真正的 `<form>`，且提交按钮带 `html-type="submit"`，回车会走浏览器的**隐式提交** → 触发 `@finish`，而 `@finish` **只在校验通过后**才回调。

---

## 10. Java：包装类型的比较必须用 `Objects.equals`

**现象**：两个「看起来相等」的 `Long` 比较结果为 false。

**原因**：`==` 对包装类型比的是引用。`Long` 在 `-128 ~ 127` 范围内有缓存，超出后会创建新对象——**小数值时看起来正常，大数值时突然出错**。

**怎么避免**：一律用 `Objects.equals(a, b)`。好处有二：值比较正确，且 **null 安全**（返回 `false` 而不是抛 NPE）。

本项目里 `Long` 主要用作 `userId` 与记录 ID——**这两个都必然超出缓存区间**，所以这不是理论风险。

## 附：这些坑的共同点

回头看，上面每一条都可以归到三类：

1. **构建环境的状态与代码无关**（1、2、3、4）——排查前先确认「我测的到底是什么」。
2. **框架的默认行为与直觉相反**（5、6、9）——默认值不总是安全的那个。
3. **预期本身是拍脑袋的**（7、8）——测量方法错了，会得到看起来很真的假数据。

第 3 类最需要警惕：**它不会报错，只会给你一个错误的结论。**
